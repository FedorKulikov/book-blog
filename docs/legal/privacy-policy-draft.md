### Резервные копии

Workflow backup.yml выполняет pg_dump только схем public и auth, шифрует dump с помощью age, передаёт зашифрованный файл в Backblaze B2 и удаляет временные файлы runner. Из этой команды не следует, что в B2 копируются сами файлы Supabase Storage: их содержимое не включено в указанный pg_dump. Нужно отдельно проверить резервное копирование объектов Storage.

Регион B2, bucket и endpoint задаются в переменных GitHub Actions; их фактические значения не читались. Срок хранения backup-объектов по исходникам не установлен.

## 4. Публичность и доступ

- Одобренные публикации доступны публично и попадают в sitemap. Публичный профиль отображает username, bio, avatar и открытые публикации.
- Публикации и профиль могут быть доступны поисковым системам и скопированы посетителями.
- Личные сообщения отделены от публичных публикаций. В проверке production 21.11.2026 обнаружена публичная настройка bucket chat-media и политика публичного чтения, несмотря на RLS у таблицы messages. 21.11.2026 после выкладки PR #42 миграция 20261208_chat_media_private.sql применена в production.
- После миграции проверено: bucket private, старая публичная политика удалена, создана политика SELECT для участников диалога, все 6 ранее загруженных объектов сохранились, роль anon видит 0 объектов. PostgreSQL CI прошёл сценарии участника, второго участника, постороннего пользователя и подделанной ссылки на чужой объект.
- Код приложения хранит новые media-ссылки как bucket-relative path, выдаёт временные signed URLs и обновляет их до истечения срока. Для старых записей поддерживается извлечение пути из legacy public URL.
- Вебвизор выключен на уровне кода (webvisor:false) до проверки маскирования. Личные сообщения и обращения поддержки помечены для исключения из session replay; поля входа и регистрации — для маскирования. Нужно проверить актуальные настройки production-счётчика Метрики.
- В проверенных пользовательских маршрутах не обнаружен self-service сценарий удаления всей учётной записи. Нужно подтвердить фактический порядок удаления аккаунта, контента, сообщений и данных из резервных копий.

## 6. География и юридический риск

Supabase проект book-blog размещён в регионе eu-central-1 (Frankfurt). Layero и Supabase — разные поставщики: российское размещение runtime Layero не переносит автоматически БД/Auth/Storage Supabase из ЕС в РФ.

Если оператор собирает персональные данные граждан РФ, требуется проверить часть 5 статьи 18 152-ФЗ о локализации операций с персональными данными в базах на территории РФ и предусмотренные законом исключения. Отдельно требуется оценить статью 12 о трансграничной передаче и статью 22 об уведомлении оператора. Нельзя считать, что уведомление о трансграничной передаче автоматически снимает требования локализации.

Если оператор или деятельность подпадает под территориальную сферу GDPR, нужно отдельно определить основания, права, сроки хранения, информацию о обработчиках и международных передачах.

Это не юридическое заключение и не утверждение о нарушении. Нужна проверка юристом с учётом страны оператора и стран пользователей. Изменение региона Supabase нельзя выполнить одним переключателем: потребуется новый проект и миграция Auth, PostgreSQL, Storage, ключей и интеграций.
