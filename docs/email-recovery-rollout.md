# Подтверждённый email для восстановления аккаунта

## Почему это отдельное подтверждение

Подтверждение email в Supabase сейчас выключено. Старые значения `auth.users.email_confirmed_at` не доказывают, что владелец аккаунта действительно контролировал почтовый ящик. Восстановление не должно полагаться на этот флаг.

Эта функция использует отдельную проверку владения ящиком:
1. Пользователь входит в свой аккаунт и открывает настройки профиля.
2. Запрашивает ссылку подтверждения на текущий email.
3. Ссылка содержит случайный токен с 256 битами энтропии, действует 20 минут и используется один раз.
4. В БД хранятся только HMAC-хеш email и хеш токена.
5. Auth Send Email Hook подавляет стандартную отправку recovery-писем. Отдельный маршрут приложения использует `auth.admin.generateLink()` без отправки письма, сверяет хеш текущего email с ранее подтверждённым значением и отправляет Resend-письмо только при совпадении.

Это не меняет режим Confirm Email для регистрации и не блокирует существующие входы.

## Внешний провайдер

Используется Resend через HTTPS API. В Supabase SMTP менять не требуется: настроенный Send Email Hook уже заменяет встроенную отправку.

Рекомендуемый отправляющий поддомен: `mail.bukleb.ru`. В Resend:
1. Создать аккаунт и добавить домен `mail.bukleb.ru`.
2. Скопировать показанные Resend DNS-записи DKIM/SPF и TXT в DNS-панель Selectel.
3. Дождаться статуса Verified у домена.
4. Создать API key с разрешением отправки email и сохранить его как секрет Layero.
5. Использовать From: `Хлеба и букв <no-reply@mail.bukleb.ru>`.

Не копируйте DNS-значения из примеров или чужих инструкций: Resend генерирует уникальные значения для конкретного домена и аккаунта. Существующие MX/TXT записи не удалять и не заменять без анализа пересечений.

## Миграция базы

После слияния PR запустить GitHub Actions → **Apply DB migrations** с параметром:

```
supabase/migrations/20261207_email_recovery_verification.sql
```

Не выбирать `ALL`: применяется только новая миграция. Workflow ведёт контрольную сумму в `ops.applied_migrations`.

## Переменные production Layero

Добавить только после подтверждения домена и создания API key:

| Переменная | Значение |
|---|---|
| `NEXT_PUBLIC_ENABLE_EMAIL_RECOVERY` | `true` |
| `EMAIL_RECOVERY_SECRET` | новый случайный секрет: `openssl rand -hex 32` |
| `RESEND_API_KEY` | ключ из Resend |
| `AUTH_EMAIL_FROM` | `Хлеба и букв <no-reply@mail.bukleb.ru>` |
| `AUTH_EMAIL_SITE_URL` | `https://bukleb.ru` |

Уже существующие серверные переменные также обязательны:
- `SUPABASE_SERVICE_ROLE_KEY`
- `AUTH_EMAIL_HOOK_SECRET`

Ни один секрет не должен иметь префикс `NEXT_PUBLIC_`, кроме самого feature flag.

## Проверка перед включением

1. Применить только указанную SQL-миграцию и проверить, что таблицы находятся в схеме `private`, RLS включён, права выданы только `service_role`.
2. Убедиться, что Auth Send Email Hook активен на `https://bukleb.ru/api/auth/email-hook` и использует тот же секрет, что `AUTH_EMAIL_HOOK_SECRET`. Не отключать hook: он блокирует встроенную отправку через публичный Auth recovery endpoint.
3. Добавить переменные Layero и выполнить production deploy.
4. Войти тестовым пользователем, открыть `/profile/edit`, запросить подтверждение и перейти по ссылке.
5. Проверить, что статус стал «Email подтверждён для восстановления».
6. На `/forgot-password` запросить сброс на этот адрес: endpoint применяет лимиты — не чаще одного запроса в минуту и трёх в час на адрес, до 20 запросов в час на IP. Письмо должно прийти, ссылка должна открывать `/auth/reset`, старый пароль должен перестать работать после смены.
7. Повторить запрос на другой, неподтверждённый или неизвестный адрес. Публичный ответ должен оставаться нейтральным, письмо не должно отправляться. Прямой вызов `/auth/v1/recover` также не отправляет письмо: Auth Hook подавляет этот канал.
8. Проверить повторное использование verification-link и ссылку старше 20 минут: обе должны быть отклонены.

## Ограничение для старых пользователей

Существующие аккаунты не подтверждаются автоматически. Каждый пользователь, пока ещё имеет доступ к своему аккаунту, должен один раз открыть настройки и подтвердить адрес. Это намеренно: доверять старому `email_confirmed_at` было бы небезопасно.

Пользователь, который уже потерял пароль, все резервные коды и все passkeys и никогда не подтверждал email через этот механизм, по-прежнему нуждается в отдельной ручной процедуре проверки личности. Нельзя автоматически подтверждать его по username или по непроверенной почте.
