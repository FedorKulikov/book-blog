# Журнал выполненных работ

Этот файл — постоянный журнал изменений проекта. Для каждой отдельной задачи или серии связанных изменений добавлять запись с датой и ссылкой на PR/коммит.

## Обязательный формат записи

- **Что требовалось:** исходная задача и ожидаемый результат.
- **Что сделано:** конкретные изменения и затронутые файлы/компоненты.
- **Как сделано:** способ реализации, важные решения и ограничения.
- **Проверки:** тесты, CI, ручные проверки и их фактические результаты.
- **Что не получилось / осталось:** невыполненное, блокеры, неподтверждённые предположения и следующие действия.
- **Публикация:** что попало в production, что осталось только в ветке/PR.

Не отмечать проверку как успешную, если она фактически не запускалась. Отделять автоматические smoke/CI-проверки от ручной проверки в браузере. Не записывать в этот публичный файл пароли, токены, секреты, приватные адреса электронной почты, персональные данные и другие чувствительные значения. Для таких сведений фиксировать только факт наличия/подтверждения и хранить точное значение вне публичного репозитория.

## 2026-11-21 — Read-only audit of self-service account deletion

- **Что требовалось:** определить следующий технический приоритет после подготовки черновика политики и выяснить, безопасно ли добавить самостоятельное удаление аккаунта.
- **Что сделано:** проверены маршруты и API в `app`, профильный интерфейс, загрузчики аватаров/изображений/медиа сообщений, внешние ключи production PostgreSQL, триггеры `auth.users`, Storage buckets, владение объектами и Storage RLS policies. Создана задача [#51 — Implement safe self-service account deletion and data cleanup](https://github.com/FedorKulikov/book-blog/issues/51) с критериями приёмки.
- **Как сделано:** GitHub-исходники проверялись без изменения файлов приложения; к production Supabase выполнены только SELECT-запросы к системным каталогам и агрегатным метаданным Storage. Содержимое пользовательских сообщений, файлов, профилей и адресов email не выгружалось. Документация Supabase по удалению пользователей и сессиям сверена на 21.11.2026.
- **Проверки / установленные факты:**
  - Самостоятельного UI-маршрута и API удаления аккаунта в текущем дереве приложения не обнаружено.
  - `auth.users` → `public.profiles` использует `ON DELETE CASCADE`; дальше удаляются посты, комментарии, лайки, закладки, подписки, conversations/messages, уведомления, отчёты, тикеты/сообщения тикетов, блокировки и action log.
  - Удаление профиля-участника приводит к удалению всей беседы и истории сообщений обоих участников; история тикетов и некоторые модерационные отчёты также удаляются каскадно.
  - `books.created_by` и `external_news.created_by` используют `ON DELETE SET NULL`, записи остаются.
  - Storage не имеет FK-каскада к auth-пользователю. В снимке production: avatars — 4 объекта, chat-media — 6, post-images — 134; только 7 объектов post-images имеют owner metadata и UUID-путь, 127 не имеют owner metadata/UUID-префикса. Это агрегатный снимок всего проекта, не подсчёт файлов конкретного пользователя.
  - Новые файлы в avatars, chat-media и post-images используют префикс UID в пути. Владелец объектов Storage должен быть очищен/переназначен до удаления Auth-пользователя; уже выданные JWT access tokens остаются действительными до истечения срока.
- **Что не получилось / осталось:** удаление не реализовано, потому что каскадное удаление чатов затронет также историю собеседников, а удаление тикетов/отчётов может уничтожить нужные записи поддержки и модерации. Нужна продуктовая политика: удалять ли беседу целиком, сохранять ли её с обезличенным участником, что делать с тикетами и модерационными данными. 127 объектов post-images без owner metadata нельзя безопасно удалять по одному только Storage owner. Нельзя тестировать такое удаление на production-аккаунтах.
- **Публикация:** код, схема БД, Storage, Auth и production-настройки не менялись. Создана только задача #51; этот журнал добавлен отдельным PR.

## 2026-11-22 — Решение по истории переписки при удалении аккаунта

- **Что требовалось:** определить поведение удаления аккаунта для личных сообщений, чтобы не уничтожать переписку второго участника, но дать удаляющему пользователю возможность убрать собственные сообщения и не оставлять лишнюю историю.
- **Что сделано:** зафиксировано два режима в задаче [#51](https://github.com/FedorKulikov/book-blog/issues/51): (1) режим по умолчанию — сохранить беседу у собеседника, заменив автора на «Удалённый пользователь»; (2) отдельный необязательный режим — удалить все сообщения и вложения, отправленные удаляющим аккаунтом, у обоих участников, но не трогать сообщения собеседника. Если после удаления своих сообщений беседа полностью пуста, удалить и пустую беседу.
- **Как сделано:** решение владельца записано в issue #51 и дополнено техническими требованиями по фактической схеме production: участники conversations и messages.sender_id сейчас имеют NOT NULL FK с ON DELETE CASCADE; существующая RLS-политика chat-media использует UUID автора в пути. Для сохранения истории потребуется изменить модель автора/связей и безопасно перенести сохраняемые вложения на нейтральные Storage-пути с проверкой доступа через беседу и сообщение. Для необратимого режима удаления потребуется удалять только сообщения и файлы выбранного пользователя.
- **Проверки:** решение сверено с ранее выполненным read-only аудитом production PostgreSQL и Storage. PR #52 с аудитом объединён в main (merge commit `86df08d76e2fefd34d86d9a11a873d579490206c`); GitHub Actions run `44948947038` завершился успешно: quality и PostgreSQL 17 migration test. По актуальной документации Supabase установлено, что объекты, создаваемые через service key, не получают пользовательский `owner_id`, а копирование создаёт объект с владельцем операции; ссылки на руководства добавлены в issue #51. Это подтверждает направление реализации, но ещё не заменяет изолированный тест в проекте.
- **Что не получилось / осталось:** реализация ещё не начиналась. До кода нужно отдельно определить судьбу тикетов поддержки, жалоб и модерационных материалов. Требуется доказать в изолированном Supabase-проекте, что service-side копирование файлов даёт объектам нейтрального владельца, корректно обновляет ссылки, сохраняет приватность вложений и не позволяет посторонним получить к ним доступ. Не выполнять destructive tests в production.
- **Публикация:** PR #52 — только документация и журнал, объединён; production-код, база данных, Storage-объекты и настройки не менялись. Настоящая запись также является документальной и остаётся в отдельном PR до CI и объединения.
