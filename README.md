# 📚 Хлеба и букв

Книжное блог-сообщество: обзоры, обсуждения и творчество вокруг книг.

**Хлеба и букв** — это площадка, где читатели пишут о прочитанном, находят книги по вкусу и
обсуждают их с другими. Вместо ленты безликих постов — каталог книг, привязанные к ним
обзоры, живые ветки комментариев и личные сообщения.

Живая версия: **https://book-blog.layero.app**

Превью рабочей ветки: **https://book-blog-dev.layero.app** (закрыто от поисковиков)

## ✨ Что умеет

| Раздел | Возможности |
|---|---|
| **Посты** | Публикация обзоров, новинок и творческих материалов; загрузка фото, теги, привязка к книге; модерация новых записей |

| **Реакции** | Лайки постов и комментариев, закладки «на потом» |
| **Люди** | Публичные профили, подписки, аватары, биография |
| **Сообщения** | Личные диалоги в реальном времени, блокировка пользователей |
| **Уведомления** | Bell-меню с непрочитанными, живое обновление |
| **Поддержка** | Тикеты с перепиской, статусы, ответы редакции |
| **Модерация** | Админка: посты на проверке, жалобы, роли (admin / moderator) |

## 🚀 Запуск локально

### 1. Клонировать репозиторий

```powershell
git clone https://github.com/FedorKulikov/book-blog.git
cd book-blog
```

### 2. Установить зависимости

```powershell
npm install
```

### 3. Настроить переменные окружения

Создай в корне файл `.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon-key>
```

Значения берутся в Supabase → **Project Settings → API**. Anon-ключ безопасно держать
на клиенте: доступ ограничен RLS-политиками. Сервисный (`service_role`) ключ проекту не
нужен и **не должен** попадать в клиентский бандл.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | да | Адрес проекта Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | да | Публичный ключ (RLS ограничивает доступ) |
| `NEXT_PUBLIC_SITE_URL` | нет | Канонический домен для `metadataBase`, sitemap и OG-тегов |
| `NEXT_PUBLIC_ENABLE_PASSKEYS` | только после настройки Supabase | Показывает вход и управление ключами доступа; включать только после настройки RP ID/origins в Supabase |
| `SUPABASE_DB_URL` | только в CI | Строка подключения для ночных бэкапов |

### 4. Запустить

```powershell
npm run dev
```

Приложение откроется на **http://localhost:3000**.

### 5. Проверка перед коммитом

```powershell
npx tsc --noEmit   # типы
npm run build      # прод-сборка
npm run lint       # eslint
```

## 🔐 Безопасность

- **RLS включён на всех таблицах.** Чтение и запись ограничены политиками; анонимный ключ
  не даёт доступа к чужим приватным данным.
- **Редактирование постов** — только автор или staff, проверка и на сервере (`getPost` +
  роль), и в RLS политике `posts_update_own_or_staff`.
- **Загрузка файлов** — лимит 5 МБ и MIME-фильтр (JPEG/PNG/WebP/GIF) на клиенте **и**
  в настройках Storage-бакета.
- **Модерация** — триггеры БД отклоняют стоп-слова и забаненных пользователей; лимиты
  действий (посты/комментарии) считаются в БД, а не в браузере.
- **Бэкапы** — ежедневный `pg_dump` шифруется `age` и уходит в приватный бакет; ключ
  шифрования хранится только офлайн.

### Восстановление пароля

Самостоятельное восстановление пароля выполняется по email. На странице
`/forgot-password` форма вызывает
`supabase.auth.resetPasswordForEmail(email.trim())`. Если адрес зарегистрирован,
Supabase Auth отправляет письмо со ссылкой через Send Email Hook. После перехода
по ссылке пользователь подтверждает её и задаёт новый пароль на `/auth/reset`.
После запроса проверьте также папку «Спам».

Если не приходит письмо или нет доступа к ящику, напишите на
`monikla1312@gmail.com` — восстановим доступ вручную.

### Send Email Hook

Send Email Hook должен оставаться включённым в Supabase. Он проверяет подпись
Standard Webhooks (`webhook-id`, `webhook-timestamp`, `webhook-signature`,
HMAC-SHA256 по исходному телу, допуск ±5 минут, constant-time сравнение).

Подтверждение регистрации и сброс пароля используют один и тот же Hook:
`signup` отправляет письмо подтверждения, а `recovery` — ссылку сброса
пароля на подтверждённый адрес `user.email`. Recovery-ссылка проходит через
`/auth/confirm` с `type=recovery` и `next=/auth/reset`.

Доставка выполняется внутри Supabase: `auth-email-hook` вызывает
`resend-mailer`, а тот отправляет письмо через Resend HTTPS API. При временной
ошибке mailer signup не блокирует регистрацию и Hook отвечает `200 {}`.
Для `recovery` и `email_change` ошибка доставки остаётся ошибкой Hook.

**Настройка:** Supabase → Authentication → Hooks → **Send Email Hook**.
Hook должен указывать на развёрнутую Edge Function
`auth-email-hook`; секрет подписи и ключ Resend хранятся в Supabase Function
Secrets. SMTP в Supabase не требуется менять. Не отключайте Hook: он обеспечивает
единый путь доставки писем и проверку подписи.

| Событие | Поведение |
|---|---|
| `signup` | Письмо подтверждения на `user.email`; при сбое отправки Hook возвращает `200 {}`, чтобы регистрация не завершалась ошибкой доставки |
| `recovery` | Письмо сброса на подтверждённый `user.email`; ссылка ведёт на `/auth/reset`; сбой mailer возвращает `502` |
| `email_change` | Письмо текущему и/или новому адресу в соответствии с Secure Email Change; сбой mailer возвращает `502` |
| Другие события | `501`, пока отдельная доставка для них не реализована |

## 🌍 Деплой

Проект развёрнут на **Layero** (сборка `npm run build`, запуск `next start`).

### Две среды: превью и продакшн

У проекта на Layero **один основной адрес и по превью на каждую ветку**:

| Ветка | Что происходит | Адрес |
|---|---|---|
| `dev` | превью: собирается каждый пуш, боевой адрес не трогается | `book-blog-dev.layero.app` |
| `main` | **боевой**: пуш в main обновляет основной адрес | `book-blog.layero.app` |

Поток работы:

1. Правки идут в `dev` — Layero собирает превью `book-blog-dev.layero.app`,
   боевой сайт при этом не меняется. Смотрим там, всё ли хорошо.
2. Когда нравится — запускаем workflow **Release to production**
   (`Actions → Release to production → Run workflow`, параметр `confirm = yes`).
   Он делает merge `dev → main`, и Layero публикует сборку на основной адрес.

Важно: превью всегда отдаётся с `X-Robots-Tag: noindex, nofollow` — поисковики
его не индексируют. Индексируется только основной адрес.

Свой домен (если подключён) показывает ту же сборку, что и основной адрес —
то есть обновляется тоже только при выпуске.

При деплое обязательно задай переменные окружения из раздела
[«Настроить переменные окружения»](#3-настроить-переменные-окружения) и убедись, что
`NEXT_PUBLIC_SITE_URL` указывает на боевой домен — от него зависят canonical-ссылки,
sitemap и превью в соцсетях.

## 🤖 Telegram-бот

В репозитории есть webhook для Telegram-бота: личное меню, ссылки на сайт, каталог книг и команда последних публикаций.

**Переменные окружения в Layero (production):**

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен, выданный @BotFather (серверный секрет) |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет для проверки входящих webhook-запросов |

Обе переменные должны быть серверными — без префикса `NEXT_PUBLIC_`. Не публикуй токен в GitHub и не отправляй его в переписке.

**Подключение:**

1. В Telegram открой [@BotFather](https://t.me/BotFather), отправь `/newbot`, задай имя и username, заканчивающийся на `bot`.
2. Добавь полученный токен и отдельный случайный `TELEGRAM_WEBHOOK_SECRET` в production Environment Variables Layero.
3. После деплоя задай эти две переменные в PowerShell (значения вводи локально, не вставляй их в чат) и запусти:
   `node scripts/set-telegram-webhook.mjs`
4. Открой своего бота, нажми Start и отправь `/id`, чтобы узнать chat ID.

Для настройки webhook скрипт использует официальный Telegram Bot API, регистрирует HTTPS endpoint `/api/telegram/webhook` и команды бота. Секреты не выводятся в лог.

**Команды:** `/start`, `/latest`, `/books`, `/id`, `/help`. Бот отвечает только в личных чатах и не хранит историю переписки или подписчиков. Чтобы бот мог отправлять пользователю первое сообщение, тот должен сам открыть бота и нажать Start.
